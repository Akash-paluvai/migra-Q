# Phase 8 — Repair Execution & Deterministic Re-Validation Engine

## 1. Executive Overview

Phase 8 introduces deterministic repair verification to MIGRA-Q.

Its **ONLY** responsibility is to execute a proposed SQL repair candidate generated by Phase 7 and deterministically prove—via re-execution in Phase 3, re-validation in Phase 4, and re-classification in Phase 5—whether the proposed repair resolves the targeted discrepancy without introducing new discrepancies or changing unrelated behavior.

```
                  Phase 7 RepairProposal (proposed_sql)
                                  │
                                  ▼
         CandidateRepairValidator (12 Pre-Execution Integrity Checks)
            ├── PASS → Proceed to DuckDB Execution
            └── FAIL → Return CANDIDATE_REJECTED (No SQL execution)
                                  │
                                  ▼
           RepairExecutor → Phase 3 ExecutionService (DuckDB Sandbox)
            ├── SUCCESS → Proceed to Re-Validation
            └── FAILED → Return EXECUTION_FAILED
                                  │
                                  ▼
         ValidationOrchestrator → Phase 4 Re-Validation (val_id_after)
                                  │
                                  ▼
          DiagnosisOrchestrator → Phase 5 Re-Classification (discrepancies)
                                  │
                                  ▼
         DiscrepancyComparator → Immutability Check + 5-Step Diff Hierarchy
                                  │
                                  ▼
         VerificationStatusDeterminer → Rule-Based Proof Chain
                                  │
                                  ▼
         PostgreSQL Persistence (repair_verifications, repair_outcomes) -> STOP
```

> [!IMPORTANT]
> **Strict Boundary Enforcement**: Phase 8 is **100% deterministic**. No Generative AI or LLM is involved. It strictly re-runs deterministic engine components (Phases 3, 4, and 5) and compares BEFORE vs AFTER states using deterministic mathematical and AST rules.

## 2. 12 Pre-Execution Integrity Checks

Before any SQL candidate is submitted to DuckDB execution, `CandidateRepairValidator` enforces 12 static integrity checks:

| # | Integrity Check Name | Status Output | Failure Code | Description |
|---|---|---|---|---|
| 1 | Proposal Status Check | `CANDIDATE_REJECTED` | `PROPOSAL_STATUS_NOT_PROPOSED` | Ensures `repair.status == PROPOSED`. |
| 2 | Non-Empty Proposed SQL | `CANDIDATE_REJECTED` | `EMPTY_PROPOSED_SQL` | Verifies proposed SQL string is not blank/whitespace. |
| 3 | Original Target SQL Exists | `CANDIDATE_REJECTED` | `MISSING_ORIGINAL_SQL` | Verifies target SQL baseline exists in proposal. |
| 4 | Unchanged SQL Rejection | `CANDIDATE_REJECTED` | `UNCHANGED_REPAIR_SQL` | Rejects repair if `proposed_sql == original_sql`. |
| 5 | Proposal Artifact Match | `CANDIDATE_REJECTED` | `REPAIR_ARTIFACT_MISMATCH` | Verifies candidate SQL exactly matches stored Phase 7 artifact. |
| 6 | SQLGlot Target Syntax Parsing | `CANDIDATE_REJECTED` | `REPAIR_SYNTAX_ERROR` | Verifies proposed SQL parses cleanly in target dialect. |
| 7 | Read-Only AST Security Policy | `CANDIDATE_REJECTED` | `READ_ONLY_VIOLATION` | Rejects DDL/DML mutation AST nodes (`INSERT`, `UPDATE`, `DROP`, `DELETE`). |
| 8 | Target Schema Structural Check | `CANDIDATE_REJECTED` | `SCHEMA_INCONSISTENCY` | Verifies proposed SQL is a valid `SELECT` statement. |
| 9 | Unknown Discrepancy Mapping | `CANDIDATE_REJECTED` | `UNKNOWN_DISCREPANCY_MAPPING` | Ensures targeted `discrepancy_id` exists in BEFORE report. |
| 10 | Required Dataset Tables Referenced | `CANDIDATE_REJECTED` | `MISSING_REQUIRED_TABLE` | Ensures all tables referenced in original SQL exist in proposed SQL. |
| 11 | Target Output Contract Preserved | `CANDIDATE_REJECTED` | `CONTRACT_ALIAS_MISMATCH` | Ensures target select aliases match original target contract. |
| 12 | AST Scope Constraints Satisfied | `CANDIDATE_REJECTED` | `SCOPE_CONSTRAINT_VIOLATION` | Enforces structural modification boundaries via `RepairScopeChecker`. |

## 3. Formal VERIFIED Proof Chain Rules

A repair is classified as **`VERIFIED`** if and only if **ALL 8 conditions** are strictly met:

$$\text{VERIFIED} \iff \begin{cases}
\text{CandidateAccepted} = \text{True} \\
\text{ArtifactMatched} = \text{True} \\
\text{ExecutionStatus} = \text{SUCCESS} \\
\text{TargetedDiscrepancyResolved} = \text{True} \\
\text{NewDiscrepancies} = 0 \\
\text{ContractPreserved} = \text{True} \\
\text{DatasetHashUnchanged} = \text{True} \\
\text{ValidationConfigHashUnchanged} = \text{True}
\end{cases}$$

### Complete Status Hierarchy:

- **`VERIFIED`**: Targeted discrepancy resolved, 0 new discrepancies, immutability & contracts satisfied.
- **`PARTIALLY_RESOLVED`**: Targeted discrepancy affected row count reduced, but not 0.
- **`NEW_DISCREPANCIES`**: Targeted discrepancy resolved/reduced, but 1+ new semantic discrepancies appeared.
- **`FAILED_VERIFICATION`**: Targeted discrepancy persists unchanged or modified without improvement.
- **`EXECUTION_FAILED`**: Runtime execution in DuckDB sandbox failed.
- **`CANDIDATE_REJECTED`**: Failed one of the 12 pre-execution static integrity checks.

## 4. 5-Step Region-Aware Discrepancy Resolution Hierarchy

`DiscrepancyDiffAnalyzer` evaluates discrepancy resolution using a 5-step hierarchy:

1. **Exact Signature Match**: If exact category + column region + SQL context signature exists in AFTER report $\rightarrow$ `PERSISTS`.
2. **Category + Region Match**: If same category and column region exists with different row count $\rightarrow$ `PERSISTS` (partially resolved / reduced).
3. **Region Replacement**: If a different category discrepancy appears in the same column region $\rightarrow$ `CHANGED` (not resolved).
4. **Absent in AFTER**: Discrepancy absent in AFTER report and no region replacement $\rightarrow$ `RESOLVED`.
5. **Unrelated Regressions**: Any discrepancy present in AFTER but absent in BEFORE $\rightarrow$ `NEW_DISCREPANCIES`.

## 5. API & CLI Reference

### API Endpoint

- `POST /api/v1/repair-verifications`: Execute Phase 8 repair verification for a proposal.
- `GET /api/v1/repair-verifications/{verification_id}`: Retrieve a stored verification result.
- `GET /api/v1/repair-verifications/{verification_id}/outcomes`: Retrieve itemized discrepancy resolution outcomes.

### CLI Command

```bash
python -m backend.repair_verification.cli verify \
  --repair-id rep-001 \
  --discrepancy-id D-001 \
  --target-dialect bigquery
```
